# Agent Operating Policy

この研究リポジトリ固有の薄い運用方針である。Skill本文やテンプレートへ研究固有ルールを埋め込まず、この文書を運用差分の正本とする。

Updated: 2026-09-10

## 1. Source of Truth

- 適用される上位指示を守り、作業範囲・採否は現在のユーザー指示と明示承認で決める。
- 実装事実は、現行コード、設定、テスト、実行環境、artifact ID・hashで確認する。
- specは意図と責務境界、steeringは検証済みの横断方針を保持する。
- memory、handoff、dashboard、agent報告、過去ログは手掛かりであり、単独では正しさの根拠にしない。
- 過去事例は生ログを保存し、通常コンテキストには「現行結論、適用条件、根拠へのパス、確認状態」だけを渡す。

## 2. Context Discipline

- cc-sddのsteeringは短いproject memoryとして維持する。
- 全spec、全ログ、全handoffを起動時に一括読込しない。まず `spec.json` や索引を確認し、対象featureの必要箇所だけを読む。
- `CODEX_RESEARCH_REPAIR_START_HERE.md` は研究修復作業の入口、`CODEX_RESEARCH_REPAIR_HANDOFF.md` は詳細根拠として必要時に参照する。
- 古い結論と現行コードが衝突した場合は、推測で統合せず差異を報告する。

## 3. Work Routing and Agents

- 小さい修正、設定変更、単発調査は直接処理し、specを強制しない。`kiro-discovery` の Path B を正規ルートとして扱う。
- 新しい責務境界、複数componentの契約変更、長期実装にはcc-sddのRequirements → Design → Tasks → Implementationを使う。
- 通常は一つのメインエージェントを編集責任者とする。サブエージェントは独立した探索、監査、テスト、ログ分析へ限定する。
- cc-sdd Skillが動的subagentを使う場合も、同じファイルや共有artifactを並行編集させず、親が実diffと決定的テストを確認する。

## 4. Safety and Authorization

- dirty worktreeの既存変更と既存artifactはユーザー所有として保持する。
- 明示依頼なしにcommit、push、PR作成、stash、履歴書換え、既存成果物の削除・移動・改名・上書きを行わない。
- `kiro-impl` autonomous modeは、その自律フロー全体が明示承認された場合だけ使用する。小刻みなcommitの許可だけでは起動せず、通常はtask指定manual modeまたは直接実装を使う。
- 長時間FVM、大量snapshot生成、新規依存、研究条件・格子・閾値・split方式の変更は、人間の明示承認なしに実行・決定しない。

## 5. Verification and Reporting

- 変更に最も近い小さいテストから実行し、必要性が確認できた範囲で統合テストへ広げる。
- 数値・物理的妥当性はテスト通過だけで判定せず、解析解、manufactured solution、収束性、保存則、最大値原理、独立参照計算のいずれかで確認する。
- AI同士の合意を独立Oracleとみなさない。不足時は `INCONCLUSIVE` とする。
- 最終報告には、変更内容、理由、検証証拠、未確定事項、実行していない高コスト作業を含める。

## 6. Research Intent Boundary

- 相談、方法の採用、実装、テスト、数値実験、スライド掲載の許可は相互に含意しない。現在の明示依頼で範囲が全て決まっていれば一括して記録でき、同じ承認を繰り返し求めない。
- 規模・所要時間を問わず、生成理論・分布・範囲・正規化・split・指標・比較条件・系列・反例・研究主張をAIが未承認で選択・変更しない。科学的影響のある「小修正」は §3 の直接処理で研究判断を省略できない。未決は選択肢と理由を返して相談へ戻す。
- 研究関連の実装・実行・資料化では、対象作業だけの `work-order.json` に採用判断・参照要件・編集先・許可コマンド・未決・本人の明示応答を残す。作業票のhashは関連する条件と資料を束縛する。AIが書ける記録やKiroのapprovedフラグを本人承認の証明とせず、現在のユーザー指示と照合する。
- 科学的結果を生む計算は小さくても数値実験であり、単体テストと呼び替えない。軽量ハーネスの最小版では数値実験の起動は本人が行う。合意済みテスト条件を変えて合格させない。
- 新規アイデア、懸念、反証は相談事項として報告できる。報告から追加実験・追加図へ自動遷移しない。既存根拠が主張と矛盾すれば、隠さず報告し、主張を保留または限定する。
- スライドは承認された主張・図・系列・処理だけで作る。出典・入力・軸・単位・留保を保持し、AIの想定問答やレビューを本人の理解確認とみなさない。説明確認前は草稿とする。
- 不足・矛盾があれば影響作業を止め、理由・証拠・対象task・戻り先・必要な判断・保全物を作業票へ残す。会話再開時はこの記録と現在の依頼を読み、関係する範囲変更だけを再承認する。
- 手順と記録形式は [使い方](../../docs/研究AIハーネス_使い方.md)。スキル・役の配置状態も同文書を確認し、未導入の役を導入済みと扱わない。共通方針は本節が正本であり、既存cc-sdd本文へ複製しない。

## 7. Small Verified Commits

- 本人の2026-09-10の依頼「gitへのコミットをこまめにしてほしい」を、このリポジトリで本人が依頼した作業について、小さなローカルcommitを継続して行う許可として扱う。依頼外の既存変更、研究方法の採用、実験実行、push・PR作成・履歴書換えの許可には広げない。現在の依頼でcommit不要と指定された場合はそちらを優先する。
- 一つの意味のある変更単位（局所実装と対応テスト、仕様・手順更新、資料構成の更新）が検証できた時点で記録する。数分ごと・一行ごとの機械的commitは不要。大きな完了時だけに溜めず、各単位の後と引継ぎ前に確認する。
- コードは対象の許可済みテスト、文書・設定はリンク・構文・範囲の検査を行い、必要な独立レビューを終えてからcommitする。草稿の文書は草稿と明記できるが、commitを研究上の承認・説明確認・科学的完了の証拠にしない。失敗を隠した成功commit、検証のための未承認実験をしない。
- 作業前のstatusとstaged差分を確認し、担当範囲の正確なpathまたはhunkだけをstageする。`git add .`、`git add -A`、`git commit -a`、依頼外変更の一括整理は使わない。既存staged内容を勝手に解除しない。同じファイルに既存変更が混在し、安全に分離できない場合はそのファイルのcommitを保留して本人へ確認する。
- commit直前にstaged差分と対象一覧を照合し、研究出力・大型binary・秘密情報・依頼外ファイルを含めない。原則として軽量なコード・テスト・設定・文書を記録する。サブエージェントはstage/commitせず、単一の編集主担当が実施する。
- 権限・Git設定・hook等で失敗した場合は状態を保持して報告する。承認機構は利用できるが、保護の解除、lock削除、hook回避、作者設定の無断変更で押し通さない。
- 最終報告にはcommit ID、記録した範囲、残した未コミット変更を短く示す。作業票がある場合も本文へcommit IDを埋めて再commitを無限に繰り返さず、Git履歴や引継ぎ報告から参照する。
