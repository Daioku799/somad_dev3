# Research & Design Decisions

## Summary

- **Feature**: `paper-rom-pipeline`
- **Discovery Scope**: Extension（既存の ROM モジュール群と旧解析スクリプト群を持つ既存システムの拡張）
- **Key Findings**:
  - 旧解析スクリプト群は必要な処理の大半を実装済みだが、研究条件（TSV本数、しきい値、パス）をソースに直書きしており、そのままでは新条件に適用できない
  - ROM の合格判定しきい値（既定 2.0 K）が、測定対象である配置効果の幅（1.6〜1.8 K）より緩く、判定として機能していない
  - 温度勾配を第3目的にする場合、素朴な定義では最大温度とほぼ完全に相関し、目的として機能しない。定義の選定を機械的に行う仕組みが必要

## Research Log

### 旧解析スクリプト群の再利用可能性

- **Context**: 新条件のデータセットに対して同等の評価を行うにあたり、既存資産をどこまで使えるかを確認する必要があった
- **Sources Consulted**: `runs/paper240_asym_v1_20260819T020802JST/` の `build_rom.jl`, `optimization_metrics.jl`, `pareto_and_power.jl`, `rom_search.jl`, `snapshot_count_study.jl`, `compare480.jl`, `stage_verification.jl`, `check_superposition.jl`
- **Findings**:
  - データ契約（`case_plan.json` の `cap` と `cases`、`cases/<name>/snapshot.jld2` の `theta`）は新旧で一致している
  - `build_rom.jl` は `c["case"]` を参照するため、新しい計画情報に `case` キーを追加する必要があった（対応済み）
  - `rom_search.jl` は `const BUDGET = 48` を持ち、TSV本数の走査ができない
  - `pareto_and_power.jl` は標本済み設計の非劣解集合のみを算出し、ε制約法を持たない
  - `snapshot_count_study.jl` は単一シードで部分集合を取るため、誤差のばらつきを示せない
  - 温度勾配に関する処理はリポジトリ全体に存在しない（`grep` で該当ゼロ）
- **Implications**: 計算ロジックをモジュールに切り出し、研究条件を注入する構造に変える。データ契約は変えない

### ROM 合格判定しきい値

- **Context**: 「ROM の誤差が最適化の改善量より十分小さい」という主張を機械的に検証する必要があった
- **Sources Consulted**: `H2-rom/src/ROMValidator/evaluator.jl:225`, `evaluate_rom_paper.jl:202`, `evaluate_rom_workflow.jl:144`, 旧データセットの `rom/summary.txt`
- **Findings**:
  - `judge_accuracy` の既定しきい値は 2.0 K
  - 旧データセットで測定した配置効果の幅は水準ごとに 1.6052〜1.8446 K
  - 旧データセットの ROM の Tmax 誤差は平均 0.0765 K、最大 0.4425 K
  - すなわち、しきい値 2.0 K は測定対象より緩く、どんな ROM でも合格してしまう
- **Implications**: しきい値を外部から指定可能にし、しきい値が配置効果の幅以上のときに警告を出す。既定値も幅より小さい値に変更する

### 温度勾配を第3目的にする際の定義依存性

- **Context**: 多目的評価の第3目的として温度勾配を検討したが、定義によって機能するかが変わる可能性があった
- **Sources Consulted**: 旧データセットの90スナップショット（各水準30件）に対する実測。`docs/PAPER_PLAN_2026-08-23.md` §3.12
- **Findings**: 水準ごとの最大温度との順位相関は次のとおり

  | 指標 | Spearman(Tmax, ·) | 設計による幅 |
  |---|---|---|
  | Tmax − Tmean | +0.95 〜 +0.97 | — |
  | 最高温層の面内温度差 | +0.89 〜 +0.90 | 1.1〜1.5 K（29〜38%） |
  | 最高温層の面内最大勾配 | +0.37 〜 +0.64 | 1.0〜1.8% |
  | 全層での面内温度差の最大 | +0.06 〜 −0.10 | 0.75〜1.14 K（4.6〜7.0%） |
  | セル別本数の二乗和 | +0.15 〜 +0.41 | — |

- **Implications**:
  - 素朴な `Tmax − Tmean` は最大温度と冗長で使えない。平均温度は総発熱と境界条件でほぼ決まり、配置ではほとんど動かないため
  - 相関が最も低い「全層での面内温度差の最大」は、旧境界条件に由来する層で値が決まっており、新条件では再測定が必要
  - したがって第3目的は事前に固定せず、新データで機械的に選定する仕組みを設ける

### 勾配指標の予測可能性

- **Context**: 勾配は温度場の微分であり、POD の打ち切り誤差が増幅される懸念があった
- **Sources Consulted**: `runs/paper240_asym_v1_20260819T020802JST/rom/holdout_predictions.tsv`、`build_rom.jl` の出力仕様
- **Findings**:
  - 既存の holdout 評価は Tmax 誤差と場の相対 L2 誤差のみを記録しており、勾配指標の予測誤差を測っていない
  - POD 再構成は `T ≈ 平均 + Σ aᵢφᵢ` であり、勾配は `∇T ≈ ∇平均 + Σ aᵢ∇φᵢ`。捨てた高次モードは細かい空間構造を持ち、微分がそれを増幅する
  - 143モード中24モードしか使っていないため、場の L2 が 0.064% でも勾配の誤差はそれより大きくなる
- **Implications**: 第3目的の採否条件に「予測可能性」を加える。実測場と ROM 再構成場の双方から同じ指標を算出して比較する

### 探索の性質

- **Context**: 最適化に GA が必要かどうかを判断する必要があった
- **Sources Consulted**: `runs/paper240_asym_v1_20260819T020802JST/rom_search.log`, `rom_search.jl`
- **Findings**:
  - 400回のランダムな初期設計からの最急降下が、すべて同一の局所最適に収束した（`400 restarts -> 1 distinct local optima`）
  - Tmax の評価は全1,874,048セルではなく上位20,000セルに限定しており、holdout 69ケースで full 再構成との差は 0.000e+00 K（限定は厳密）
  - 実測での ROM 1評価は 0.064 ms（ベンチマーク）
- **Implications**: 多点スタート最急降下で十分であり、GA は不要。相異なる局所最適の個数を出力して単峰性を示す

## Architecture Pattern Evaluation

| Option | Description | Strengths | Risks / Limitations | Notes |
|---|---|---|---|---|
| 旧スクリプトを run ディレクトリに複製して改造 | 既存 `.jl` をコピーし定数を書き換える | 最短で動く。既存の挙動を保てる | 同一ロジックが複数の run に散在し、単体テストができない | 締切前の即効性はあるが、Day 3 の追加要件で破綻する |
| **モジュール層 + 薄いドライバ層（採用）** | 計算ロジックを `H2-rom/src/` に切り出し、run 固有の条件を注入 | 単体テスト可能。将来の run で再利用可能。出力が run 内に閉じる | 初期の切り出しコストがかかる | 新規要件（勾配指標、N走査、ε制約）はいずれも新規実装であり、どのみちモジュール化が必要 |
| 既存モジュールを全面改修 | `ROMValidator` や `PaperEvaluation` に新機能を追加 | 資産の集約 | 既存の完了済みスペックの契約を壊す。回帰リスクが高い | しきい値の既定値変更のみに留める |

## Design Decisions

### 決定1: 計算ロジックをモジュール化し、研究条件をドライバから注入する

- **決定**: `PipelineData` / `ObjectiveMetrics` / `SearchOptimizer` / `PipelineReport` を新設し、run 固有のパスと条件は `common.jl` から注入する
- **理由**: 新規要件6件のうち5件（勾配指標、予測精度比較、N走査、最悪探索、ε制約）は既存実装が存在せず、いずれにせよ新規に書く必要がある。書くならテスト可能な形にするほうが、締切前の手戻りが少ない
- **代替案**: 旧スクリプトの複製と改造。Day 2 までなら速いが、Day 3 の探索要件で結局モジュール化が必要になる
- **トレードオフ**: 初期コストは増えるが、単体テストが書けるため実装中の手戻りが減る

### 決定2: 既存モジュールの契約を変更しない

- **決定**: `PODEngine`, `ROMInterpolator`, `PaperEvaluation` は呼び出すのみ。`ROMValidator` はしきい値の既定値と警告のみ変更する
- **理由**: これらは完了済みスペック（`pod-engine`, `rom-validator`, `rom-paper-evaluation`）が所有しており、契約変更は該当スペックの再検証を要する。締切前にその余裕はない
- **トレードオフ**: `ROMValidator` の判定ロジックが本パイプラインの要求と完全には一致しない可能性があるが、しきい値を外部指定にすれば実用上足りる

### 決定3: 第3目的を事前に固定せず、機械的に選定する

- **決定**: 温度場由来の候補5件と設計変数由来の候補2件を算出し、独立性（相関の上限）と予測可能性（誤差 vs 幅）の2条件で選定する
- **理由**: 旧データでの測定から、定義によって機能するかが大きく変わることが分かっている。かつ最も有望だった候補は旧境界条件に由来する層で値が決まっており、新条件では結果が変わりうる
- **代替案**: セル別本数の二乗和に固定する。確実だが、熱応力・タイミングスキューの観点での文献的正当性が弱い
- **トレードオフ**: 選定が実行時に決まるため、後続の探索と作図が第3目的に依存する。中間成果物として保存し依存を明示する

### 決定4: 探索アルゴリズムは多点スタート最急降下を維持する

- **決定**: GA を導入せず、既存の近傍定義（1本をセル間で移動）と多点スタートを踏襲する。最大化は符号反転で実現する
- **理由**: 400リスタートで相異なる局所最適が1つしか見つかっておらず、探索空間が単峰である証拠がある。GA の導入は複雑さに見合わない
- **トレードオフ**: 真に多峰な条件（第3目的を変えた場合など）では最適を逃す可能性がある。相異なる解の個数を出力し、多峰性が現れたら判断材料にする

### 決定5: ε制約法の刻み数は呼び出し側が指定する

- **決定**: `epsilon_constraint_front` は上限値の列を引数で受け取り、モジュール内部で刻みを決めない
- **理由**: 探索時間は水準数 × 刻み数に比例する。締切前は刻みを粗くし、余裕があれば細かくするという調整を、コード変更なしで行えるようにする

## Risks

| リスク | 影響 | 緩和策 |
|---|---|---|
| 勾配指標がいずれも採否条件を満たさない | 第3目的が設計変数由来に退避し、文献的正当性が弱くなる | 退避先（二乗和）でも多目的評価は成立する。原稿では「勾配は予測精度が不足したため採用しなかった」と限界に明記する |
| 内挿検証が不合格 | TSV本数を連続に扱う正当化ができない | 水準を1つ追加（133本・約1.5時間）で回復可能。Day 2 に判明するため日程内 |
| 424ケースの一括読み込みでメモリ不足 | 解析が実行できない | 温度場は列ベクトルに変換して元配列を保持しない。必要なら Tmax と指標のみを先に算出する2段構成に切り替える |
| 第3目的が実行時に決まるため後続が壊れる | 探索と作図が失敗する | 中間成果物（`third_objective.json`）に保存し、後続ドライバは必ずこれを読む |
| 旧スクリプトとの結果不一致 | 移植の誤りに気づけない | 旧データセットに対して新モジュールを走らせ、旧出力と一致することを確認する回帰テストを設ける |
