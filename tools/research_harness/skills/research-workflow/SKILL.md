# 研究実装の受渡し

最初に `.kiro/steering/agent_policy.md` を読み、記録作成・再開時は `docs/研究AIハーネス_使い方.md` の「作業票」「差戻し」を読む。

1. 現在のユーザー指示、対象specの必要箇所、当該work-order.jsonを照合する。旧会話・handoff・候補案は許可ではない。なければ雛形を使って対象task・採用判断・未決を短く起票し、operations.implementとoperations.testで編集先・許可テストを分け、必要な承認を得る。事務的整形はAIが行い、本人へJSON編集を要求しない。
2. 科学的決定を研究要件として固定する。生成理論・分布・範囲・正規化・split・指標・比較対象の不足はresearch-consultへ戻す。設計者の裁量で研究方法を選ばない。
3. 新しい責務境界なら既存Kiroの要件→レビュー・本人承認→設計→レビュー・本人承認→タスク→本人承認を使う。既存specは必要箇所だけ更新する。Kiro本文は複製・改変しない。`-y` / `--auto` を本人承認の代替に使わず、各phaseの明示承認なしに次へ進めない。未決の有無やAIが書いたapprovedフラグだけでは前進しない。
4. 実装前に `python3 -B tools/research_harness/harness.py check <作業票> --action implement --write <対象ファイル>`、テスト前に `--action test --command-json '<argvのJSON配列>'` を使う。複数編集先は--writeを繰り返す。実コマンド・全書込先・cwd・呼出し先コードの影響を照合する。argv一致はコードや副作用の安全証明ではなく、研究計算か曖昧なら本人へ戻す。合格は本人承認の証明でも権限拡張でもない。
5. 明示承認済みの内容を再確認し続けない。ユーザー応答の参照と引用を忠実に記録し、承認されたhashを後から新しい内容へ更新しない。関連内容が変われば影響する作業を止める。
6. 実装は単一編集担当。Kiroは対象task指定のmanual modeを用い、commitを含む自律モードは使用しない。許可テストのみ実行する。小さい計算でも研究結果を生むものは実験であり、テストと呼び替えない。最小版では数値実験は本人が起動する。
7. 対象diffと局所テストを独立レビューへ渡す。追加実験・別理論の提案は相談事項として返し、自動採用しない。失敗を閾値・格子等の無断変更で隠さない。検証した変更単位はagent_policy.md §7に従って主担当が小さくcommitし、ID・対象範囲・未検証・残りの変更を報告する。commitを研究承認やpush許可に読み替えない。

不足時は当該作業票のstate.phaseをblockedとし、理由・証拠・影響task・戻り先・必要な判断・保全物を記録して影響作業を停止する。科学判断→相談、ソフトウェア契約→spec、バグ→実装。再開は解消根拠と元の許可範囲を確認し、範囲変更なら本人の再承認が必要。別作業の完了を消さない。

モデルと委任上限は使い方の「モデル」に従う。モデル変更は作業権限を広げない。
