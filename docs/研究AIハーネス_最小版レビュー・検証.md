## 計画レビューの結論

方向性は採用可能。ただし元の17タスク全体を最小版として一括導入する案は過大であり、以下へ縮小して実装する。

1. 共通方針の研究承認境界を補う。
2. 相談・Kiro受渡し・資料化の3つの短いSkill、4つの読取り役定義を作る。
3. 作業票の必須項目・現在範囲hash・許可種別・掲載内容を検査する、Python標準ライブラリのみの単一CLIを作る。
4. 差戻し・再開・本人の説明確認は短い記録と手順で扱い、自動状態機械を作らない。

ユーザーの「この計画をレビューして。私の設計思想を実現するための最小限の軽量ハーネスとして実現できそうなら、実装まで進めて。」を、レビューに基づくこの小さい実装範囲の依頼と解釈した。研究方法や数値実験の採用許可とは解釈しない。

Kiro discoveryでは、研究ソフトウェアの新しい契約・責務境界を追加する実装ではなく、既存運用の方針・設定・局所検査の追加に縮小したため、最小版はPath Bの直接実装とする。元計画P0.3の独立specと17タスクの全面実装は行わない。将来、迂回不能なrunnerや複数componentの契約を導入する場合は別specで要件→設計→タスクをレビューする。既存の科学的状態・specの承認フラグは変更しない。

## 独立レビューへの対応

Sol/highを指定した読取り専用レビューで、元計画をそのままMVP化する案はREJECTED。以下の指摘を採用した。

| 指摘 | 最小版の対策 |
|---|---|
| 「小作業」「短時間」が未承認研究判断の抜け道になる | policy §6で規模を問わない境界を明記。実験は本人起動 |
| AI可書込のapproved記録は本人承認を証明できない | CLIの結果はRECORD_CHECK_PASSに限定。現在の本人応答を別途照合し、自己承認しない |
| task IDだけでは入力・系列・変換・対象を固定できない | scope、ID、root、選択した参照内容をhash化。系列・変換・軸・主張と出力hashも照合 |
| read-onlyだけではPython/Julia計算を禁止できない | 相談の安全な入口は実行ツール非接続。役定義は行動規約と明記し、強制隔離を称さない |
| 状態機械・全host展開・自動最適化は過剰 | 既存Kiroと一作業一記録を流用。新しい全体dashboard・DB・サービス・比較実験は作らない |

利用量は必要時に記録された値を集計する小関数のみ。常時収集や自動モデルルーティングはない。参考値から効率優位を断定しない。
